# gh-issue-create

Issueは人が読むものなので、正確に伝わる言語で書く。

## 手順

1. **種類を判断する**

   バグ報告 / 機能要望 / タスク のどれか。ユーザーの発言から明らかでなければ聞く。

2. **テンプレートを決める**

   次の優先順位で決める。上のものがあれば、それに従う。

   1. リポジトリに`.github/ISSUE_TEMPLATE/`（配下のmarkdownファイル、または`config.yml`）があれば、手順1で決めた種類に対応するものを探す（ファイル名やfrontmatterの`name`/`about`で判断する）。frontmatter（`---`で囲まれた部分）は本文に含めない。
   2. なければ、単一ファイル形式の`ISSUE_TEMPLATE.md`（リポジトリのroot・`.github/`・`docs/`のいずれか）があれば、それを使う。
   3. リポジトリテンプレートがなく、AGENTS.md（またはCLAUDE.md）にIssue本文の構成指定があれば、それに従う。
   4. どれもなければ、以下のデフォルトテンプレートを使う。

   **バグ報告**
   ```markdown
   ## 概要
   [何が起きているか、1〜2文]

   ## 再現手順
   1. ...
   2. ...

   ## 期待する挙動

   ## 実際の挙動
   ```

   **機能要望**
   ```markdown
   ## 概要
   [提案する内容、1〜2文]

   ## 背景・目的
   [なぜ必要か]

   ## 提案内容
   [具体的にどうするか]
   ```

   **タスク**
   ```markdown
   ## 概要
   [やること、1〜2文]

   ## やること
   - [ ] ...

   ## 完了条件
   [何をもって完了とするか]
   ```

   どちらの場合も、実際に関係ある項目だけ埋め、無理に空欄を作らない。

3. **言語を決める**

   AGENTS.md（またはCLAUDE.md）に言語の指定があれば、それに従う。指定がなければ日本語で書く（title・bodyとも同じ言語）。

4. **確認してから投稿する**

   タイトルと本文をユーザーに見せる。OKが出たら:

   ```bash
   gh issue create --title "タイトル" --body "本文"
   ```

   `--label`はユーザーが指定し、かつそのリポジトリに既に存在する場合のみ付ける。テンプレートのfrontmatterに`labels`が書かれていても、勝手に推測して付けない。

5. **結果を報告する**

   `gh issue create`が返すIssueのURLを伝える。

## 注意

- バグ報告の再現手順は、実際に見聞きした内容のみ書く。不明な点はユーザーに確認する。
- タイトルは一覧で見て内容が分かる具体性を持たせる（「バグがあります」ではなく「ログイン後にセッションが切れる」）。
