# gh-pr-create

PRはレビューする人間が読むものなので、正確に伝わる言語で書く。会話の内容だけで推測せず、必ず実際のdiffを見て書く。

## 手順

1. **現在のブランチとbase branchを確認する**

   ```bash
   git branch --show-current
   ```

   base branch（マージ先）は憶測しない。次の順で決める。

   - このプロジェクトのAGENTS.md（またはCLAUDE.md）にbase branchの指定があれば、それを使う（例: 「PRは`develop`へ」）。
   - 指定がなければ `git branch -r` でリモートの長期ブランチを確認する。`main`（または`master`）しかなければそれを使う。
   - `main`と`develop`のように複数の長期ブランチが存在し、どちらへのPRか判断できない場合は、憶測せずユーザーに直接聞く。

   現在のブランチがbase branch自体でないことも確認する（`main`から`main`へのPRは作らない）。

2. **pushされているか確認する**

   ```bash
   git status
   ```

   未pushのコミットがあれば、ユーザーに確認してから:

   ```bash
   git push -u origin <branch>
   ```

3. **ブランチ全体の変更を見る（直近のコミットだけでなく）**

   手順1で決めたbase branchを使う:

   ```bash
   git log <base>..HEAD --oneline
   git diff <base>...HEAD
   ```

4. **言語を決める**

   タイトルと本文で役割が違うので、言語も別に決める。

   - **タイトル**: コミットメッセージの規約（英語・命令形など）に揃える。squash and mergeの運用では、GitHubがPRタイトルをそのままsquash後のコミットメッセージ（subject）として使うため、揃っていないとコミット履歴の書式が崩れる。merge commitやrebase mergeの運用ではタイトルが直接コミットメッセージになるわけではないが、その場合もPRタイトルは変更履歴やリリースノートの一覧として参照されることが多く、書式が揃っている方が検索・把握しやすい。AGENTS.md（またはCLAUDE.md）に別の指定があれば、そちらを優先する。
   - **本文**: レビュアーとのコミュニケーションが目的なので、正確に伝わる言語を使う。AGENTS.md（またはCLAUDE.md）に指定があればそれに従い、なければ日本語で書く。

5. **PR本文を作成する**

   テンプレートは次の優先順位で決める。上のものがあれば、それに従う。

   1. リポジトリに`.github/PULL_REQUEST_TEMPLATE.md`（または`.github/PULL_REQUEST_TEMPLATE/`配下のファイル）があれば、その構成に従う
   2. AGENTS.md（またはCLAUDE.md）にPR本文の構成指定があれば、それに従う
   3. どちらもなければ、以下のデフォルトテンプレートを使う

   ```markdown
   ## 概要
   [このPRで何をするか、1〜2文]

   ## 変更内容
   [主な変更点を箇条書き]

   ## 変更理由
   [なぜこの変更が必要か]

   ## テスト方法
   [実際に確認した方法。確認していないなら正直にそう書く]
   ```

   どのテンプレートを使う場合も、実際に関係ある項目だけ埋め、無理に空欄を作らない。必要な時だけ`## 影響範囲`やスクリーンショットを追加する。

6. **確認してから投稿する**

   タイトルと本文をユーザーに見せる。OKが出たら、手順1で決めたbase branchを明示して投稿する:

   ```bash
   gh pr create --base "<base>" --title "タイトル" --body "本文"
   ```

   `--base`は省略しない。手順1で確定させた値を必ず使う。

7. **結果を報告する**

   `gh pr create`が返すPRのURLを伝える。

## 注意

- テスト方法を捏造しない。実際に確認したことだけを書くか、確認していないと正直に書く。
- ブランチに無関係な変更が複数混ざっている場合は、作成前に指摘する。コミットメッセージのルールと同じで、1つのPRは1つの論理的な変更に絞った方がレビューしやすい。
- base branchの判定を誤ると誤った相手にPRが出るので、AGENTS.mdに書いていない・複数の長期ブランチがある場合は、必ずユーザーに確認してから進める。
